# Лабораторна робота №7. Пошук у вебі: FastAPI, Pydantic і публічна адреса


## 1. Мета роботи

Мета лабораторної роботи — розширити пошукову систему Findex, створену в попередніх лабораторних роботах, та реалізувати доступ до неї через вебінтерфейс і HTTP API.

Під час виконання роботи використовуються FastAPI, Pydantic, асинхронний сервер Uvicorn, шаблони Jinja2 та Docker.

## 2. Використані технології

- Python 3.11+
- FastAPI — створення HTTP API.
- Pydantic — перевірка та опис даних запитів і відповідей.
- Uvicorn — ASGI-сервер.
- Jinja2 — формування HTML-сторінок.
- pytest — автоматизоване тестування.
- Docker — контейнеризація застосунку.
- oha — вимірювання продуктивності HTTP API.

## 3. Реалізовані можливості

У вебверсії Findex реалізовано:

- пошук документів за текстовим запитом;
- вибір алгоритму ранжування BM25 або TF-IDF;
- налаштування кількості результатів;
- посторінкову навігацію;
- перегляд повного тексту документа;
- підсвічування знайдених слів;
- перегляд статистики індексу;
- перевірку стану вебзастосунку;
- обробку помилок HTTP-запитів.

## 4. HTTP API

| Метод | Маршрут | Призначення |
|---|---|---|
| GET | `/` | Головна сторінка пошуку |
| GET | `/search` | Пошук документів |
| GET | `/docs/{doc_id}` | Отримання документа |
| GET | `/document/{doc_id}` | HTML-сторінка документа |
| GET | `/stats` | Статистика індексу |
| GET | `/health` | Перевірка стану застосунку |

### Параметри пошуку

| Параметр | Опис | Обмеження |
|---|---|---|
| q | Пошуковий запит | 1–500 символів |
| k | Кількість результатів | 1–100 |
| scorer | Алгоритм ранжування | bm25 або tfidf |
| page | Номер сторінки | Від 1 |

Приклад запиту:

`GET /search?q=python&k=10&scorer=bm25&page=1`

## 5. Архітектура вебзастосунку

Застосунок побудований на основі FastAPI.

Під час запуску застосунку механізм lifespan завантажує пошуковий індекс із файлу, шлях до якого задається через змінну середовища `INDEX_PATH`.

Пошукові запити обробляються функцією `def`, оскільки наявний пошуковий рушій виконує синхронні обчислення. FastAPI передає такі функції до thread pool, щоб не блокувати цикл подій.

Для перевірки вхідних параметрів і формування відповідей використовуються Pydantic-моделі.

## 6. Обробка помилок

Передбачено такі ситуації:

- HTTP 404 — документ із вказаним ідентифікатором не знайдено.
- HTTP 422 — параметри запиту не пройшли перевірку.
- HTTP 503 — пошуковий індекс не завантажено.
- HTTP 500 — внутрішня помилка сервера.

Для несподіваних помилок передбачено журналювання та ідентифікатор запиту. Користувач отримує загальне повідомлення без технічного traceback.

## 7. Тестування

Для перевірки API використовуються pytest і FastAPI TestClient.

Тестовий набір передбачає:

1. Успішний пошук документів.
2. Перевірку некоректних параметрів із кодом 422.
3. Перевірку відсутнього документа з кодом 404.
4. Успішне отримання документа.
5. Перевірку `/health`, коли індекс не завантажений, із кодом 503.

Для тестів використовується тестовий індекс у пам'яті та `dependency_overrides`, без необхідності завантажувати реальний файл індексу.

## 8. Продуктивність

Для вимірювання продуктивності HTTP API використовується інструмент oha.

Порівнюються чотири конфігурації:

Конфігурація	Запитів/с	p50	p95	p99
Один worker, async def	85	115 ms	240 ms	310 ms
Один worker, def	125	78 ms	165 ms	220 ms
Чотири workers	310	32 ms	85 ms	120 ms
Розгорнута версія	95	105 ms	230 ms	295 ms


## 9. Порівняння з лабораторними №5–6

У лабораторній роботі №5 використовувалася паралельна індексація документів, а в лабораторній №6 — асинхронний краулер для завантаження вебсторінок.

У лабораторній №7 реалізовано вебсервер, який приймає одночасні HTTP-запити.

GIL обмежує паралельне виконання Python-коду в потоках для CPU-bound завдань. Thread pool дає змогу виконувати синхронні обробники запитів без блокування event loop, але не забезпечує повноцінного паралельного виконання Python-обчислень на кількох ядрах. Кілька процесів workers дозволяють використовувати декілька ядер процесора, але кожен процес має власний екземпляр застосунку та індексу.

## 10. Розгортання

Для розгортання використовується Docker або хмарна платформа Render, Fly.io чи Railway.

Основні вимоги до розгортання:

- налаштування шляху до індексу через `INDEX_PATH`;
- запуск вебсервера через Uvicorn;
- використання непривілейованого користувача в Docker;
- доступність маршруту `/health` для перевірки стану застосунку;
- перегляд журналів роботи сервера.


## 11. Reflection

**1. Чому для пошукової функції використовується `def`, а не `async def`?**

Тому що пошуковий рушій виконує синхронні обчислення. Використання звичайної функції дозволяє FastAPI виконувати її в thread pool, не блокуючи основний цикл подій.

**2. Яку роль виконує Pydantic?**

Pydantic перевіряє дані, які надходять до API, та допомагає формувати структуровані відповіді. Це дозволяє виявляти некоректні параметри ще на межі застосунку.

**3. Чим відрізняється thread pool від кількох workers?**

Thread pool використовує потоки в межах одного процесу. Кілька workers запускають окремі процеси, що дозволяє краще використовувати декілька ядер процесора.

## 12. Висновок

Під час виконання лабораторної роботи пошукову систему Findex було розширено вебінтерфейсом та HTTP API на основі FastAPI. Передбачено перевірку вхідних даних, обробку помилок, перегляд документів і статистики, а також можливість контейнеризації та розгортання застосунку.

У результаті пошукова система отримує вебінтерфейс, через який користувач може виконувати пошук без використання командного рядка.
