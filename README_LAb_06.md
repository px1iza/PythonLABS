# Лабораторна робота №6. Асинхронний вебкраулер на asyncio

## 1. Мета роботи

Мета лабораторної роботи — ознайомитися з асинхронним програмуванням у Python за допомогою `asyncio` та реалізувати асинхронний вебкраулер для збору інформації з вебсторінок.

Під час виконання роботи розглянуто:

- цикл подій (Event Loop);
- корутини та оператор `await`;
- асинхронне виконання мережевих запитів;
- обмеження кількості одночасних запитів;
- обробку помилок і повторні запити;
- правила доступу до сайтів через `robots.txt`.

## 2. Опис реалізації

Асинхронний краулер реалізований у модулі `src/findex/crawler.py`.

Основні компоненти:

| Компонент | Призначення |
|---|---|
| `crawl()` | Асинхронний обхід вебсторінок |
| `fetch()` | Завантаження сторінки з обробкою помилок |
| `RobotsCache` | Перевірка та кешування правил `robots.txt` |
| `PageParser` | Витягування тексту та посилань із HTML |
| `canonicalize_url()` | Нормалізація URL для уникнення дублікатів |
| `retry_delay()` | Розрахунок затримки перед повторним запитом |

Для виконання HTTP-запитів використовується бібліотека `httpx`, а для асинхронного керування завданнями — `asyncio`.

У програмі використовуються:

- `asyncio.TaskGroup` — керування групою асинхронних завдань;
- `asyncio.Semaphore` — обмеження одночасних запитів;
- `asyncio.timeout` — обмеження часу очікування;
- `asyncio.Queue` — організація черги URL;
- `asyncio.sleep` — асинхронні затримки.

## 3. Дотримання правил доступу до сайтів

Перед завантаженням сторінок краулер перевіряє файл `robots.txt` відповідного сайту.

Параметри роботи:

- **User-Agent:** `FindexCrawler/1.0`
- **Обмеження:** до 200 сторінок за один запуск.
- **Джерело правил доступу:** файл `robots.txt` сайту, який обрано для обходу.
- **Область обходу:** початковий хост.

Для запуску потрібно самостійно обрати сайт, дозволений для автоматизованого обходу, або використати власний сайт чи локальне дзеркало. Перед запуском необхідно перевірити правила доступу.

## 4. Обробка помилок

Під час завантаження сторінок передбачена обробка таких ситуацій:

- HTTP 429 — перевищення дозволеної частоти запитів;
- HTTP 5xx — помилки сервера;
- тайм-аут — перевищення часу очікування відповіді;
- інші HTTP 4xx — помилка клієнтського запиту без повторного завантаження.

Для помилок 429, 5xx та тайм-аутів передбачено до трьох повторних спроб. Між спробами використовується експоненційна затримка з випадковою складовою. Якщо сервер передає `Retry-After`, ця інформація використовується для визначення затримки.

### Приклад логу збою

Нижче наведено демонстраційний приклад журналу під час отримання HTTP 429:

```text
INFO URL=https://example.org/page/1 status=429 bytes=0 time=0.214
WARNING Retry URL=https://example.org/page/1 status=429 attempt=1 delay=1.35
INFO URL=https://example.org/page/1 status=200 bytes=4521 time=0.308
```

Цей приклад демонструє ситуацію, коли сервер тимчасово обмежив кількість запитів, після чого краулер повторив запит і отримав успішну відповідь. Це ілюстрація формату логу, а не фактичний запис запуску.

## 5. Порівняння продуктивності

Для демонстрації впливу кількості одночасних запитів розглядаються три режими роботи:

- concurrency = 1;
- concurrency = 5;
- concurrency = 20.

У кожному режимі передбачається обробка 200 сторінок.

### Демонстраційні результати

**Увага:** наведені значення є модельними та не отримані в результаті фактичного вимірювання програми.

| Concurrency | Сторінки | Час виконання, с | Сторінок/с | Помилки | Peak RSS, MB |
|---:|---:|---:|---:|---:|---:|
| 1 | 200 | 42.8 | 4.67 | 2 | 38.4 |
| 5 | 200 | 11.6 | 17.24 | 2 | 42.1 |
| 20 | 200 | 5.2 | 38.46 | 2 | 48.7 |

У демонстраційному прикладі зі збільшенням concurrency зменшується час обходу сторінок. Це пояснюється тим, що під час очікування мережевої відповіді цикл подій може виконувати інші корутини.

Водночас збільшення кількості одночасних запитів підвищує використання пам'яті та навантаження на сервер.

## 6. Чому asyncio ефективний для мережевих операцій

У лабораторній роботі №5 використовувалося паралельне виконання задач, орієнтованих на обробку даних.

У лабораторній роботі №6 розглядається інший тип навантаження — очікування мережевих відповідей.

Асинхронне програмування дозволяє одному потоку обслуговувати багато мережевих запитів. Коли одна корутина очікує відповідь від сервера через `await`, Event Loop може перемкнутися на іншу корутину.

Тому для задач, які переважно очікують введення-виведення (I/O-bound), asyncio може бути ефективнішим за послідовне виконання.

## 7. Обмеження частоти запитів

У програмі передбачені обмеження одночасних запитів і затримка між запитами до одного хоста.

Ці обмеження потрібні для:

- зменшення навантаження на сервер;
- дотримання правил доступу;
- уникнення надмірної кількості запитів;
- зменшення ймовірності отримання HTTP 429.

Збільшення concurrency не означає, що потрібно надсилати необмежену кількість запитів. Важливо враховувати можливості сервера та правила `robots.txt`.

У результаті виконання лабораторної роботи було розглянуто принципи асинхронного програмування в Python та реалізовано вебкраулер на основі `asyncio`.

## 10. Reflection

### 1. Чому 20 одночасних запитів в одному потоці можуть бути швидшими за послідовне виконання?

Тому що під час очікування відповіді від сервера одна корутина не блокує весь потік. Event Loop може перемикатися на інші корутини, які вже готові до виконання.

### 2. Чому потрібно обмежувати кількість запитів до одного хоста?

Щоб не перевантажувати сервер, дотримуватися правил доступу та уникати блокування через надмірну кількість запитів.

### 3. Що станеться, якщо виконувати індексацію всередині асинхронної корутини безпосередньо?

Якщо індексація виконує тривалі синхронні CPU-операції, вона блокуватиме Event Loop. Через це інші корутини не зможуть своєчасно виконуватися. Тому індексацію краще запускати окремо після завершення збору сторінок.
