# Лабораторна робота №5

## Паралельна індексація: потоки, процеси та GIL

### Мета роботи

Дослідити конкурентність і паралелізм у Python, порівняти послідовну, потокову та процесну побудову інвертованого індексу findex, виміряти час виконання, використання CPU та пам'яті, а також дослідити вплив GIL.

### Реалізація

У лабораторній роботі було реалізовано:

- `build_partial()` — створення часткового індексу для групи файлів.
- `merge()` — об'єднання часткових індексів.
- `serial` — послідовна індексація.
- `threads` — індексація за допомогою потоків.
- `processes` — індексація за допомогою окремих процесів.
- Вимірювання часу виконання та використання пам'яті.
- Перевірку унікальності `doc_id`.
- Обробку помилок воркерів.

### Запуск

Послідовна індексація:

```bash
findex index --data data --output index.bin --workers 1 --executor serial
```

Потокова індексація:

```bash
findex index --data data --output index.bin --workers 4 --executor threads
```

Процесна індексація:

```bash
findex index --data data --output index.bin --workers 4 --executor processes
```

### Вимірювання продуктивності

Для вимірювання продуктивності використовується окремий скрипт:

```bash
uv run python scripts/benchmark_lab05.py --data data --runs 3 --output benchmark
```

Для кожного режиму використовуються 1, 2, 4, 8 та кількість воркерів, що відповідає кількості логічних ядер процесора.

Кожен варіант запускається щонайменше тричі. Для порівняння використовується медіанне значення.

### Python 3.13t

Для встановлення Python 3.13t використовується uv:

```bash
uv python install 3.13t
uv python pin 3.13t
uv sync --python 3.13t
```

Перевірка стану GIL:

```bash
uv run python scripts/gil_status.py
```

У free-threaded збірці Python 3.13t GIL може бути вимкнений. Це дозволяє потокам виконувати Python-код паралельно на декількох ядрах.

Перевірка виконується за допомогою:

```python
import sys

print(sys._is_gil_enabled())
```

Для порівняння потоків у звичайній та free-threaded версіях Python потрібно провести окремі вимірювання. Результати цих запусків слід додати до таблиці після фактичного тестування.

### Reflection

#### Чому потоки під GIL не прискорили індексацію?

Індексація є переважно CPU-bound задачею, тобто основне навантаження припадає на процесор. У звичайному Python існує GIL — глобальне блокування інтерпретатора. Воно не дозволяє декільком потокам одночасно виконувати Python-байткод в одному процесі. Тому навіть якщо створити декілька потоків, вони не зможуть повноцінно використовувати декілька ядер для обчислень.

#### Чому процеси можуть прискорити індексацію і чим це оплачено?

Кожен процес має власний інтерпретатор Python і власний GIL. Тому декілька процесів можуть виконувати обчислення паралельно на різних ядрах.

Однак процеси потребують додаткових ресурсів. Необхідно створювати процеси, передавати їм дані та отримувати результати. Для передачі об'єктів використовується pickle, що також потребує часу.

Wall time показує реальний час виконання програми, а CPU time — сумарний процесорний час. Під час паралельної роботи CPU time може бути більшим за wall time. Також процеси використовують додаткову оперативну пам'ять.

#### Де проявляється закон Амдала?

Закон Амдала показує, що прискорення програми обмежується тією частиною роботи, яку неможливо виконувати паралельно.

У нашій програмі часткова індексація розподіляється між воркерами, але після цього потрібно об'єднати результати за допомогою `merge`. Ця операція виконується окремо та обмежує максимальне прискорення.

#### Що змінилося в Python 3.13t?

Python 3.13t підтримує free-threaded режим, у якому можна виконувати Python-код у декількох потоках без GIL.

Це дозволяє краще використовувати декілька ядер для CPU-bound задач. Проте потрібно враховувати синхронізацію спільних даних та накладні витрати.

Для перевірки використовується `sys._is_gil_enabled()`.

### Гонки даних

GIL не гарантує безпечність усіх операцій зі спільними змінними.

Наприклад, якщо декілька потоків одночасно змінюють спільний `Counter` або список, частина оновлень може бути втрачена.

Для вирішення цієї проблеми можна використовувати `threading.Lock` або потокобезпечні черги.

У нашій реалізації кожен воркер створює власний частковий індекс, а головний процес об'єднує результати через `merge`. Це дозволяє уникнути одночасної зміни спільного словника індексу.

### Висновок

У лабораторній роботі було реалізовано паралельну побудову інвертованого індексу з використанням потоків і процесів.

Було розглянуто вплив GIL, порівняно різні способи виконання та підготовлено інструменти для вимірювання продуктивності.
